# 13 数据同步优化记录（超越原版）

> 日期：2026-10-29。应用户指示"能优化就优化"，对原版数据同步架构做了三处优化。

## 一、原版的同步策略（被优化的基线）

- 同步时机：启动、网络恢复、窗口聚焦、切前台、定时轮询——**每次都拉整包快照（1MB+）**
- 快照只存在**内存**：每次刷新页面都从零重拉
- 无重试链：失败只能等下一轮轮询

## 二、三处优化（cba-lamps-glue.js 的 installDataRelay）

| # | 优化 | 实现 | 效果 |
|---|---|---|---|
| 1 | **增量按日拉取** | meta 对账 → 只拉快照缺的日期（`games?date=`） | 日常访问拉 1 天几十 KB，而非整包 1MB |
| 2 | **增量持久化**（核心） | 合并成功后把增量存 localStorage（`cba-relay-delta-v1`，上限 3MB），启动时先应用本地增量再走网络 | **重载秒级恢复新鲜数据**（实测 8 秒内快照到今天，原版要 1-2 分钟重拉）；中继只补真正的增量 |
| 3 | **失败自愈** | 请求级重试 3 次（4s/8s 间隔，兜住云函数冷启动 450）+ meta 失败 15 秒后整轮重跑 | 弱网/冷启动不卡死 |

## 三、实测对比

| 场景 | 原版 | 新版 |
|---|---|---|
| 每次刷新页面 | 重拉整包快照（1MB+，几十秒） | **8 秒内恢复**（localStorage 增量 + 只查 meta） |
| 日常每日首次打开 | 拉整包 | 拉 1 天增量（几十 KB） |
| 云函数冷启动/弱网 | 等下轮轮询 | 3 次重试 + 自动重跑 |
| 断网 | 降级用内存快照 | 降级用持久化快照（更新鲜） |

实测数据：重载后 8 秒 updatedAt=2026-10-29T09:43、王哲林 5 场、schedules 含新场次；delta 373KB（远低于 3MB 上限）。

## 四、实现要点（维护注意）

- 持久化 key：`cba-relay-delta-v1`（结构 `{games:[relay格式]}`）；升级结构时换 key 后缀
- 配额保护：>3MB 或 localStorage 不可用时静默放弃持久化，游戏照常（回到原版行为）
- 合并幂等：schedules 按 id 替换、player.games 按 gameId 去重，重复合并无副作用
- 同步时机（仿原版+轮询）：启动(+5s)、聚焦、切前台可见、每 5 分钟；幂等安全
- **glue 版本号当前 ?v=20261029f**——改 glue 必须升版本号（浏览器缓存教训）
